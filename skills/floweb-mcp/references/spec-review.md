# 审查 Spec

## 三个维度

### 欠规范的地方
实现者需要猜测的决策点：
- 模块/文件名模糊
- 新增/修改 schema 时缺少数据形状
- 模块间接口归属不明确
- 缺少预期失败场景的错误处理
- Phase 顺序关系不清晰

### 设计级逻辑错误
- Phase N 删除了 Phase N+2 依赖的概念
- Spec 自相矛盾
- 假设数据形状与实际代码不符
- 竞态条件或顺序问题
- 缺少去重机制

**不标记：** 类型检查器会抓的、格式化工具会处理的、代码风格问题。

### 规范符合度
- 是否有所有必要章节？
- Phase 是否 commit 大小？
- Success criteria 是否验证最可能出错的东西？
- 有没有过度设计？

## 输出格式

```
# Spec Review: [名称]

## 欠规范的地方
- [问题]

## 设计错误
- [问题]

## 规范符合度
- [确认或问题]

## 结论
[2-3 句：可以实施吗？必须先修什么？]
```

## 规则

1. 审查**计划**，不是实现
2. 不要标记工具会抓的问题
3. 聚焦实现者会踩的坑
